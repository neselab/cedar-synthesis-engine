# Policy underwriting authorization requirements

Case: case-222
Domain: policy_underwriting
Selected actions: approveException, bindPolicy

## Purpose

Determine whether a user may perform each of these operations: approve an underwriting exception; bind an insurance policy.
Each request names one user, one action, one resource, and trusted context supplied by the host application. Decide whether to allow that request using the current recorded facts.
The permissions do not perform state changes or assert an execution order between actions.

## How permissions apply

For each action, allow access if and only if the stated requester and resource types match and ALL requirements in that action section hold. Otherwise deny access. Deny requests for actions not listed here.
Each unless clause waives only the requirement in its own sentence. It never grants access or waives other requirements.
If a condition in an If sentence is false, only that sentence imposes no additional duty; every other requirement still applies.
Users may hold multiple roles. Role membership and ownership are distinct facts. Money is expressed in integer USD cents. Times are UTC. Daily time windows recur every day of the week.
Brackets identify exact fields or entity types. Role and status values identify entities of their declared types. True and false are Boolean values. Every listed interval includes only the endpoints explicitly stated.
Optional-field presence is explicit in the rules. A guarded predicate is false if a field it needs is missing; preserve the enclosing negation, condition, or waiver. Requirements about presence remain binding.
The separately supplied Cedar schema defines entity types, fields, optionality, action types, and valid enum vocabulary. Use that schema unchanged. Its declarations alone add no authorization requirements; declaring schedule fields does not impose a time window.

## Permission to approve an underwriting exception
Action: approveException
Requester type: User.
Resource type: Application.

Allow this action if and only if all the following requirements hold:

- Access requires that at least one of [the user has the "SeniorUnderwriter" role; the user has the "UnderwritingManager" role; the user has the "ChiefUnderwriter" role].
- Access requires that the application's premium [resource.premium] is at least 0 USD cents.
- Access requires that the user [principal] equals the application's assigned underwriter [resource.assignedUnderwriter].
- If the application's coverage lines [resource.coverageLines] contains "controlled_liability", access requires that the coverage exception review has been completed [context.coverageExceptionReviewCompleted].
- If the application's premium [resource.premium] exceeds 100,000 USD cents, access requires that at least one of [the user has the "UnderwritingManager" role; the user has the "ChiefUnderwriter" role].

## Permission to bind an insurance policy
Action: bindPolicy
Requester type: User.
Resource type: Application.

Allow this action if and only if all the following requirements hold:

- Access requires that at least one of [the user has the "Underwriter" role; the user has the "SeniorUnderwriter" role; the user has the "UnderwritingManager" role].
- Access requires that the user's authority level [principal.authorityLevel] is one of [0; 1; 2; 3].
- Access requires that the application's premium [resource.premium] is at least 0 USD cents.
- Access requires that the application's risk tier [resource.riskTier] is one of [0; 1; 2; 3].
- Access requires that the user's authority level [principal.authorityLevel] is at least the application's risk tier [resource.riskTier].
- Access requires that the application's coverage lines [resource.coverageLines] contains "excess_surplus".
- Access requires that the application's product code [resource.productCode] matches the Cedar wildcard pattern "CONTROLLED-*".
