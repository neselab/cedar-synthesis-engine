# Comp authorization authorization requirements

Case: case-102
Domain: comp_authorization
Selected actions: applyComp, authorizeComp

## Purpose

Determine whether a user may perform each of these operations: apply a complimentary benefit; authorize a complimentary benefit.
Each request names one user, one action, one resource, and trusted context supplied by the host application. Decide whether to allow that request using the current recorded facts.
The permissions do not perform state changes or assert an execution order between actions.

## How permissions apply

For each action, allow access if and only if the stated requester and resource types match and ALL requirements in that action section hold. Otherwise deny access. Deny requests for actions not listed here.
Each unless clause waives only the requirement in its own sentence. It never grants access or waives other requirements.
If a condition in an If sentence is false, only that sentence imposes no additional duty; every other requirement still applies.
Users may hold multiple roles. Role membership and ownership are distinct facts. Money is expressed in integer USD cents. Times are UTC. Daily time windows recur every day of the week.
Brackets identify exact fields or entity types. Role and status values identify entities of their declared types. True and false are Boolean values. Every listed interval includes only the endpoints explicitly stated.
Optional-field presence is explicit in the rules. A guarded predicate is false if a field it needs is missing; preserve the enclosing negation, condition, or waiver. Requirements about presence remain binding.
The separately supplied Cedar schema defines entity types, fields, optionality, action types, and valid enum vocabulary. Use that schema unchanged. Its declarations alone add no authorization requirements; declaring schedule fields does not impose a time window.

## Permission to apply a complimentary benefit
Action: applyComp
Requester type: User.
Resource type: CompAuthorization.

Allow this action if and only if all the following requirements hold:

- Access requires that at least one of [the user has the "FrontDeskAgent" role; the user has the "GuestServicesHost" role].
- Access requires that the user's comp authority level [principal.compAuthorityLevel] is one of [0; 1; 2; 3].
- Access requires that the comp authorization's comp value [resource.compValue] is at least 0 USD cents.
- Access requires that the comp authorization's guest tier [resource.guestTier] is one of [0; 1; 2; 3].
- Access requires that the comp authorization's status [resource.status] equals the "authorized" status [CompAuthorizationStatusValue].
- Access requires that the comp authorization's comp type [resource.compType] contains "beverage".
- If the comp authorization's comp value [resource.compValue] exceeds 2,500 USD cents, access requires that the host confirms completion of the additional review [context.applyCompV8ReviewCompleted].

## Permission to authorize a complimentary benefit
Action: authorizeComp
Requester type: User.
Resource type: CompAuthorization.

Allow this action if and only if all the following requirements hold:

- Access requires that at least one of [the user has the "ShiftManager" role; the user has the "FrontOfficeManager" role].
- Access requires that the comp authorization's comp value [resource.compValue] is at least 0 USD cents.
- Access requires that the comp authorization's item count [resource.itemCount] is at least 0.
- Unless all of [the vip escalation has been declared [context.vipEscalationDeclared]; the user has the "FrontOfficeManager" role], access requires that the user [principal] differs from the comp authorization's requester [resource.requestedBy].
- Access requires that the comp authorization's loyalty group [resource.loyaltyGroup] is the same hierarchy node as or descends from the user's assigned group [principal.assignedGroup].
